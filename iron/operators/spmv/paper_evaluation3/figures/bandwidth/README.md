# 論文用・実効帯域幅図

再生成: IRON リポジトリのルートから

```bash
python3 -m iron.operators.spmv.plot_paper_bandwidth
```

実重みの図だけを更新する場合は末尾に `--only real` を付ける。

元データは `paper_evaluation3/` の `real_weights_w5_t5_idle0s_between0s.jsonl`
（5行列 × 4方式）と `synthetic_paper_w5_t5_idle0s_between0s.jsonl`
（11条件 × 10 seed × 4方式）。全件、warmup 5回、時間計測5回、明示的な待機なし。
作図コードは入力レコード数、方式、タイミング方式とバイト数を検査する。

| 図 | 内容 |
| --- | --- |
| `real_bandwidth.pdf` | 実重み5件の方式別実効帯域幅。CVの低い順に各方式の点を線で結ぶ。各点はその行列の5回計測の平均レイテンシーから算出した値。 |
| `density_bandwidth.pdf` | 非ゼロ率別・方式別の10行列平均帯域幅。誤差棒は10行列間の標本標準偏差。行NNZの目標CVは0.44。 |
| `cv_bandwidth.pdf` | 行NNZの目標CV別・方式別の10行列平均帯域幅。誤差棒は10行列間の標本標準偏差。非ゼロ率は10%。横軸は測定設定を等間隔に並べたもので、線の傾きはCVあたりの微分を表さない。 |
| `combined_bandwidth_vs_io.pdf` | 上記の全460件を1件1点で示す。実重みだけを強調せず、形と色で方式を識別する。横軸は対数目盛。 |

実重み図の線は5件の値を目で追いやすくするための接続であり、行列の形状も
異なるため、CVだけを変えた連続的な性能曲線ではない。

実効帯域幅は `run_test` と同じ定義で、NPUへ渡す論理的な入力バッファと
出力バッファの合計バイト数を、5回の平均 `result.npu_time` で割り、
10進の GB/s にした値。横軸の MB も100万バイト単位。
コンパイル時間やホスト側での準備時間は含まず、ハードウェア上の実DRAM
トランザクション量を直接測った帯域幅でもない。

Sparse方式ではベクトル `x` とSELLの行マップがcontrolに含まれるので、
これらを再加算しない。元JSONLの `packed_a_bytes + control_bytes + y_transfer_bytes` は、Sparseの2方式だけ
`run_test` の実際の合計より一律64 B少ない。作図ではJSONLに記録された
実効帯域幅と平均レイテンシーから `run_test` の合計バイト数を整数として
復元し、その差が64 Bであることを検査している。これ以外の不一致はエラーにする。

この統合散布図は、転送量が小さいケースほど実効帯域幅が低くなり得ることを
示す記述的な図であり、固定起動費用だけが原因だと証明するものではない。
方式間では計算量、DMA配置、ベクトルの複製数も異なる。

## 統合図で下振れする点

総I/Oバイト数が同じでも、8列の仕事量が揃わなければ最も遅い列が
実行時間を決める。例えば実重み L0 `v_proj` のSELL-C-σは
`column_blocks=[135,170,151,185,216,166,325,318]`、
最大/平均ブロック数は1.56。5回の時間は319.6–321.1 µsで安定しており、
32.20 GB/sへの下振れは単発の計測スパイクでは説明できない。
合成行列 `cv_1.89`/seed 1003のSlice-ELLも最大/平均が1.23で、
5回の時間は585.6–587.9 µsと安定し、43.33 GB/sに留まる。
これらは列負荷不均衡と整合するが、DMA・計算待ちをtraceで分離した
原因確定ではない。

一方、合成行列 `density_10`/seed 1007のSlice-ELLは最大/平均が
1.04と小さいにもかかわらず、時間が
`[281.728,283.337,300.458,377.247,328.967]` µsと計測中に増加し、
5回平均では41.46 GB/sになった。これは時間揺れを含む点であり、
列不均衡の例と一緒に扱わない。総I/O量だけで全点が一本の曲線に
乗ると期待しない理由は、このように複数ある。
